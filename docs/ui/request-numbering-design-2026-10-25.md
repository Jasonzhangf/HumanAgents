# 请求编号：响应错误不消耗编号

状态：用户已确认的设计增补，待执行与验收。来源：2026-10-25 用户要求“上次出现响应错误的情况下，下一次不加号码，错误不会增加编号”。本文件为此规则的唯一设计入口，供当前 MVP 交互与恢复工作引用。

## 用户可见行为

请求发生响应错误时，不消耗当前请求编号；下一次请求继续使用该编号。只有该次请求取得契约认可的成功响应，后续请求才使用下一个编号。

例如，上一次成功为第 7 号，接下来第 8 号请求响应错误，则下一次仍为第 8 号；连续错误仍为第 8 号；第 8 号成功后，下一次才为第 9 号。首次请求失败，下一次仍为第 1 号。

编号是面向用户的请求序号。响应错误必须保留真实错误与历史记录，不能为保持连续编号隐藏失败或伪造成功。沿用号码不表示重用内部 interaction、request、turn 或 Journal 身份，不得覆盖历史、倒退 Journal 序列，或将不同输入误判为同一次幂等请求。

## 并发决定：成功提交时分配正式编号

并发采证回执m1792946055391-3340表明当前receive允许多个interaction先接收。设计不新增single-flight拒绝或排队，也不把“接收时不可变地发出编号”当作既有需求。正式编号只在权威成功回执提交时分配；接收、处理中和响应错误均不预占正式编号。UI在这些阶段显示处理中/失败及原内部身份关联，不能把待用N冒充已经发出的正式编号。

因此前述“8号错误→下次仍8”表示待用成功序号仍为8；失败记录自身没有消耗正式序号。并发A/B都在第7次成功后接收时，不给两者预发8；若B先成功，则B正式为8，A之后成功则为9；A失败则无正式号，下一成功仍为9。多个失败不递增。正式编号一经成功提交不可改，成功顺序以同一持久化owner的提交顺序确定，不能以HTTP返回先后或模型文本推断。

复用ExplicitIntake已有同步state提交/持久化边界，分配与该interaction成功事实在同一次保存中完成；相同interaction/revision成功重试只返回已有正式编号，不再加一。不得先加counter后另写成功状态，不新增队列、锁框架或第二账本。先以最小并发反例证明现有owner可串行提交；若真实持久化跨进程不具此保证，报告实际owner/写入模型，不能假定已有原子性。此为Alice对执行未知的设计裁定，不是产品实现或验收。
